## 2. The current blocker — missing content, not a wrong field

```
fault = 0x1
PC    = ELF 0x9aebd7   (Ghidra 0x9bebd7 — see the correction below)
sym   = CSRGameScrollBGDraw::OnUpdate(CMUpdatable*)
LR    = ELF 0x1bc23d7  _Znwj
r0 = 0x00000001   r3 = 0x00004001     identical in 5/5 legs
```

The faulting instruction **[RECOVERED]**:

```asm
009bebd2  ldr  r0,[sp,#0x54]     ; local vector<shared_ptr<CMImageNode>>::_M_start
009bebd4  ldr  r0,[r0]
009bebd6  ldr  r1,[r0]           ; <-- FAULT: uninitialised heap, r0 == 1
009bebd8  ldr.w r1,[r1,#0x90]
009bebdc  blx  r1
```

No emptiness check on that path. `r0 == 1` is **not a sentinel** — it is the first word of a
buffer that `reserve(0x10)` allocated but nothing ever wrote. The vector has **zero elements**.

Why it is empty **[RECOVERED]**: `CSRGameScrollBGDraw::Load` attaches a `CMImageNode` child
**only in the `else` branch of `if (CMImageNode::LoadAnim(...) == 0)`**. All 30 layers failed,
so no child was ever attached. `Load` logs this itself:

```
23:48:26.812  [WRN] [Load] Cannot find The resource(_D4)
23:48:27.034  BLUSTONE_ARM: signal=11 code=1 fault=0x1     222 ms later, same process
```

The 30 resource names are `_A0.._A9`, `_D0.._D9`, `_E0.._E9`, built as
`CMFormat("%s_%s", ENV_INFO.name, CSRStaticData.<field>)`.

**And `ENV_INFO` comes from `environments.csv`, which does not exist.**

I verified this directly, and it is worse than "not served":

```
Get-ChildItem -Recurse -Filter "environments*" recovered-assets\   -> nothing
Get-ChildItem -Recurse analysis\reconstructed-resources -Filter *.csv -> 0 files
Select-String *.jet -Pattern "environments"                          -> no plaintext hit
```

There is no `.csv` file anywhere in the workspace outside the Android SDK and Python test
fixtures. **The replica has never possessed this file.** No JSON edit can make `_D4` resolve;
this is a content-recovery problem with a different owner than every fixture problem we have
hit so far.

## 3. The most important correction in this round

The tester flagged the 30 `LoadAnim2 '_A*'/'_D*'/'_E*'` misses as pre-existing and
**withdrew** them as a lead, having measured 30/leg in both r014 and r015. That was correct
method — but the wrong conclusion.

The native analysis shows they were **masked, not inert**: r014 died ~31 ms after
`/mission/Start`, *before* the background layers were ever attempted. r015 survives
~600–800 ms, which is long enough to reach `InitBackground` and fail all 30. Same count, same
names, completely different significance.

This is the second time in two days that a measurement was right and the inference drawn from
it was wrong (the first was `show_thumbnail`'s type, which a control leg correctly falsified).
**Keep measuring; keep re-deriving what a measurement means.** The count being stable did not
mean the cause was stable.

## 4. Corrections to my own claims

- **I dropped a hex digit.** I wrote "PC `+0x9aebd7` = Ghidra `0xaaebd7`". It is
  `0x9aebd7 + 0x10000 = 0x9bebd7`. `0xaaebd7` is 983 KB past `OnUpdate`'s end; an agent caught
  this before trusting it, and its first Ghidra batch decompiled an unrelated function. The
  `+0x10000` rule was re-verified three ways against Ghidra's own `Memory` bytes.
- **`AGENTS.md` §11's `MakeStageInst` at `0x925798`** is `CSRExploreMirage::MakeStageInst`.
  There are **three** `MakeStageInst` symbols in this binary. Never attribute by nearest
  preceding symbol name.

## 5. A confound that has now been fixed

`/mission/Start` replied `idempotent:true` with r010's `battle_id` for **six** consecutive
reports. It was not an idempotency window at all — it was a **one-way latch**: `startMission`
tested only `state === "active"`, and the only thing that ever clears that is
`/mission/Complete`, which the client has never once reached. Restarting the server could not
clear it.

Now fixed: idempotent within a window (default 30 s, `BLUSTONE_MISSION_START_IDEMPOTENCY_SECONDS`,
`0` = always fresh, `forever` = the old behaviour for reproducibility). The window length is a
**[POLICY DECISION]**, not recovered — the native binary shows only that the client *can*
retry a request (`CPVHTTPRequest::GetRetryCnt`), which justifies having a window, not its
length.

Two real defects found alongside it: `battle_id` was not unique (it was
`local-${pvid}-${Date.now()}`, colliding within a millisecond), and `/mission/Complete`
re-paid 10 gold for an already-cleared stage whenever any battle was active.

## 6. Operational warning — AP is draining

The live account is at **`ap 44/50`**, and `/mission/Start` consumes 1 AP per fresh start with
