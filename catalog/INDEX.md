## 1. The two findings that matter most

### 1.1 `card_id == skill_id`, exactly, for all 113 characters

`CHAR_STR_RO`, `SKILL_REF_RO` and `SKILL_TAG_RO` all carry **the same 113 ids**.
Not a shared numbering scheme — the *same* ids. Card `001` is skill `001`; card
`056_1` is skill `056_1`. Every one of the 113 has **exactly 5 skill slots**
(`row` 1..5). [RECOVERED]

This means the server can build `/reference/GetCard` entirely from the three
LevelDB tables, and the `skill_list` field has no lookup problem at all. It also
means the id space `001..098` + `_1` variants is **player-card-specific**:
monsters do not live in it.

The 5 slots are structurally uniform across all 113 cards [COMMUNITY-SOURCED,
wiki `Activation` tables, verified on all 103 named cards]:

| slot | activation |
|---|---|
| 1 | Active — the special move, costs Rage |
| 2 | Follows active |
| 3 | Passive — fires at battle start |
| 4 | Follows active |
| 5 | Passive — fires at battle start |

The slot-1 EN text states the Rage cost verbatim ("Uses N Rage Gauge"), so Rage
cost is **[RECOVERED]**, not community data. See §4.

### 1.2 `CHAR_STR_RO` was only half-dumped before, and the missing half was free content

`analysis/recovered-data/leveldb-tables/char-str.tsv` has 7 columns. The
underlying `CHAR_STR_RO` table has **1033 rows** and **9 fields**:

| field | in the old TSV? |
|---|---|
| `TITLE` (121) | yes |
| `VICTORY` (121) | yes |
| `SUMMARY` (113) | yes |
| `WEAPON` / `ARMOR` / `ACCESSORY` (113 each) | yes |
| **`WEAPON_DESC` (113)** | **NO — recovered here** |
| **`ARMOR_DESC` (113)** | **NO — recovered here** |
| **`ACCE_DESC` (113)** | **NO — recovered here** |

That is **339 rows of real shipped equipment flavour text** that the project did
not have. Exported to [`data/card-catalogue.tsv`](legacy-catalogue-data/card-catalogue.tsv) and
inlined into every `cards/NNN.md`.

A second table, **`SKILL_EFFECT_RO` (230 rows)**, was present in
`all-tables.json` but had never been dumped to TSV either. It supplies the
**display name of each skill slot** (e.g. card 001 slot 2 =
"Penetrate Invincible / Defense-"). Exported to
[`data/skill-effect.tsv`](legacy-catalogue-data/skill-effect.tsv).

### 2.3 Awakened (`_1`) rows ship **no separate art package**

All 15 `_1` rows lack a `C<n>_1.jet`. [RECOVERED filesystem] That is expected: awakening restyles an existing card rather than adding one.
The project already knows the mechanism — `AGENTS.md` §11 records
`CSRSkin::FindWornSkinByCardRefId(&local_e0)` in `MakeStageInst`. So:

- **[INFERRED]** `res_prefix` for an awakened card should be its **base** card id
  (`004_1` -> `C004`), with the awakened look supplied as a *skin*.
- **Rejected:** inventing a `C004_1` prefix. There is no such package and
  `res_prefix` is resolved against a resource map, so a miss yields an empty
  layer set — the exact failure mode in `AGENTS.md` §16.2 row 4.
- Each base card does carry `A`/`B`/`C` alternates (`C004A/B/C.jet`), which are
  the costume art, **not** awakening art.

### 7.2 Must stay MOCK — `[INFERRED-FIXTURE]`

**Base stats.** Nothing publishes them. Placeholders must be:

- **[INFERRED-FIXTURE]** derived from `LEVELING.jet` §5.1 so that the *role*
  relationship the real game uses is preserved: multiply a common base by
  `bomber 0.85 hp` / `support 0.80 hp`. That is recovered, so at least the
  **ratios** are right even though the absolute numbers are invented.
- **[INFERRED-FIXTURE]** scaled by rarity. The only hard anchor is
  `LEVELING.jet` chunk 19: at level 30 the power spread is 4,000 (1★) / 9,700
  (2★) / 31,200 (3★) / 86,400 (4★) / 185,900 (5★). Power is not HP, so this
  bounds the *shape* of the curve but not the stat split.
- **[INFERRED-FIXTURE]** A reasonable placeholder range: 1★ HP ~2,000–4,000 /
  ATK ~300–600; 2★ ~1.3x; 3★ ~3x; 4★ ~8x; 5★ ~20x, each then multiplied by
  the role factor from §5.1. **These numbers are invented and must be labelled
  as such in the OpenAPI docs.**

**Skill magnitudes.** `SKILL_REF_RO` ships the *formula*
`-1*(stat*(8+2*rank))*(value+value_up*skill_level)/10000` but not `value` or
`value_up`. The formula is real and the server should use it verbatim — that
already fixes the damage curve's shape. Only `value`/`value_up`/`duration` need
synthesising. **[INFERRED-FIXTURE]** `value` ~1000–3000 at skill level 1,
`value_up` ~15% of `value` per level, `duration` 4 s for the bleed/debuff
templates the EN text names.

**Monster HP/ATK/DEF and the whole monster skill block.** No anchor at all.
**[INFERRED-FIXTURE]** keep them small and monotonic in `rank`, apply the §5.2
multipliers server-side rather than baking them in, and send an empty
`skill_list` — the client has no monster skill-name table, so an empty list
cannot mismatch anything.

**Gear stat values.** Only the category is known (weapon→ATK, armor→DEF,
accessory→HP). **[INFERRED-FIXTURE]** per-piece growth 1..50 with
modification gates at 10/20/30/40 and 1 jewel slot, +1 at level 20
([COMMUNITY-SOURCED] FAQ L333, L344 — those two numbers *are* sourced).

### 7.3 Ship as REAL but flag as unsourced

`rarity`/`rank` (star count). It comes only from the wiki. It is *extremely*
likely correct — the 1★/2★/3★/4★/5★ bands line up with the costlier awakening
materials (FAQ L504: A1=30 crystals + 30k rupees ... A3=100 + 150k) and with
the chunk-19 power table’s five rank bands — but it is not recovered. Label it

### 7.4 Do not ship at all

- The 8 non-card rows (`901`–`904`, `912`–`914`, `x914`) as inventory. They are
  trainer-NPC and item strings. If `/reference/GetCard` keys on them the client
  will try to instantiate a card from an empty row — which is very likely what
  produced the five `SRCard.cpp(731)` assertions in `AGENTS.md` §16.6 item 2.
  **[INFERRED]**, moderate confidence, worth testing.
- The 15 orphaned `C5xx` art packages as cards. No string table backs them.
